1. 문제

사람인·잡코리아의 AI 추천은 이력서의 직무명과 공고의 직무명을 맞춘다. 광고 3년 뒤 프론트엔드로 옮긴 지원자에게는 프론트엔드 공고만 나온다. 그런데 "AI 자동화 빌더"처럼 이름이 아직 정착되지 않은 직무는 공고 제목에 그 이름이 없다. 본문을 읽어야 보인다.

그래서 AI 관련 키워드 12개로 공고를 모으고, 본문을 LLM으로 읽혀 실제 수행 업무 기준 17개 직무로 다시 분류했다.

1,323수집한 공고 (사람인 + 잡코리아)
44%"AI" 키워드로 잡혔지만 실제로는 일반 사무·마케팅·디자인
82재분류 후 지원자 프로필에 "적합"으로 판정된 공고

3. 만든 뒤 찾은 문제와 개선

동작하는 사이트를 만든 다음, 코드를 다시 읽고 DB에 직접 물어봐서 문제 세 가지를 찾았다. 각각 별도 커밋으로 고치고, 같은 스크립트로 전/후를 쟀다. 측정은 각 쿼리 200회 반복 평균, 로컬.

Issue 1 · 정확도

"React"를 검색하면 React Native, React Query가 섞여 나온다

발견
DBeaver에서 역량 표기를 묶어 세어봤다. SELECT skill, COUNT(*) FROM job_skill WHERE skill LIKE '%React%' GROUP BY skill → 46가지 표기.
원인
LLM이 추출한 문자열("React/Next.js/TypeScript", "React 또는 Vue")을 그대로 저장하고 LIKE '%검색어%'로 비교했다.
수정
원문 표기 → 표준명 매핑 테이블 skill_alias를 규칙으로 생성. 복합 표기는 구분자로 나눠 여러 표준명에 대응. 검색은 표준명 정확 일치.
Before
WHERE skill LIKE '%React%'
After
JOIN skill_alias al ON al.raw = s.skill
WHERE al.canonical = 'React'

매칭되는 표기 종류46종1종

남은 한계: 규칙 매핑이라 새 표기가 들어오면 규칙을 추가해야 한다. 6,203종 중 규칙에 안 걸린 표기는 원문이 그대로 표준명이 된다.

Issue 2 · 인덱스

검색할 때마다 job_skill 8,285행을 전부 훑는다

발견
쿼리 앞에 EXPLAIN QUERY PLAN을 붙여 실행. SCAN job_skill이 찍혔다. SEARCH면 인덱스를 타는 것이고 SCAN이면 전체 탐색이다.
원인
기본키 외에 인덱스를 하나도 만들지 않았다. 1,323건이라 체감이 없었을 뿐이다.
수정
검색·조인에 쓰이는 컬럼 6개에 인덱스. job_skill(skill), job_skill(job_id), skill_alias(canonical), job_analysis(role), job_category(job_id), job(company_id).

Issue 3 · N+1

통계 페이지가 쿼리를 28번 날린다

발견
stats/page.tsx에서 직무 14개를 map으로 돌며 필수·우대 각각 getRoleSkills() 호출. 반복문 안의 쿼리, 전형적인 N+1.
수정
윈도우 함수 ROW_NUMBER() OVER (PARTITION BY role, kind)로 직무·종류별 상위 12개를 쿼리 한 번에. 직무별 총계는 CTE로 미리 구해 조인.
Before · 28 queries
stats.map(s => (
  <Bars items={getRoleSkills(s.role, "required")} />
  <Bars items={getRoleSkills(s.role, "preferred")} />
))
After · 1 query
WITH totals AS (SELECT role, COUNT(*) total FROM job_analysis GROUP BY role)
SELECT … FROM (
  SELECT a.role, s.kind, al.canonical, COUNT(DISTINCT s.job_id) n,
         ROW_NUMBER() OVER (PARTITION BY a.role, s.kind
                            ORDER BY COUNT(DISTINCT s.job_id) DESC) rn
  FROM job_skill s JOIN job_analysis a … JOIN skill_alias al … JOIN totals t …
  GROUP BY a.role, s.kind, al.canonical)
WHERE rn <= 12
28회 (N+1)1회 (윈도우)
인덱스 없을 때63 ms28 ms
인덱스 있을 때13 ms28 ms
측정이 예상과 달랐다. 인덱스를 넣고 나니 이 규모(8천 행)에서는 28회 인덱스 조회가 윈도우 집계 1회보다 빠르다. 윈도우 쿼리는 호출마다 전체 행을 집계하기 때문이다. 그래도 1회 쿼리를 유지했다. 이 페이지는 빌드 시 한 번만 실행되는 정적 페이지라 15ms 차이가 의미 없고, 직무가 100개로 늘면 N+1은 200회가 되지만 윈도우 쿼리는 그대로 1회이며, 외부 DB로 옮기면 네트워크 왕복 횟수가 시간을 지배한다. 배운 것은 "N+1은 항상 느리다"가 아니라 "측정해서 결정한다"였다.

5. 아직 남은 것

  • 데이터가 배포에 박혀 있다. 읽기 전용 SQLite를 번들에 포함하므로 새 공고를 반영하려면 재배포해야 한다. 외부 DB(PostgreSQL)로 옮기면 db.ts의 연결 부분만 바뀌고 SQL은 거의 그대로다.
  • 마감 지난 공고가 노출된다. 마감일이 "~ 09/30(수)" 같은 문자열이라 비교가 안 된다. 날짜로 파싱해서 저장하고 기본 제외해야 한다.
  • OFFSET 페이지네이션. 45페이지라 지금은 무관하지만, 규모가 커지면 커서 방식으로.
  • 분류는 LLM 추정치. 직무·역량 오분류가 있다. 사람인 이미지 공고 137건은 본문 없이 제목·카테고리로만 분류됐다.
